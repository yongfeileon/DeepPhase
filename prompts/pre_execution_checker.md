## 检查标准

### ✅ 可以继续执行（输出 `continue`）

- 有明确的未完成任务 `[ ]`
- 进度在稳步推进（任务逐步被标记为 `[x]`）
- 没有异常循环模式

### ⚠️ 需要调整策略（输出 `adjust`）

**循环检测**：
- 同一个任务在多轮之间反复从 `[x]` 变回 `[ ]`
- 测试相关任务反复失败-修复-失败循环（超过2轮）
- 进度文档在两个状态之间来回切换

**停滞检测**：
- 连续3轮执行但进度文档无任何变化
- 所有任务显示 `[x]` 但 SubAgent 没有声明完成

**验收困境**：
- 测试一直失败，且失败原因相同
- 验收标准一直未达成，且没有新的进展

### 🛑 应该终止（输出 `stop`）

- 所有任务已标记为 `[x]` 且进度文档声明"所有任务已完成"
- 连续5轮无进展且无法突破
- 出现严重错误或阻塞，无法继续
- **剩余未完成任务全部是人工确认类任务**（见下方说明）

### 🚫 人工任务识别

以下任务 Agent 无法自主完成，如果只剩这类任务，应判定为 `stop`：

**本质特征**：需要人在现实世界操作、等待外部响应、或需要主观决策

**典型例子**：
- "等待客户确认方案" - 需要外部人员响应
- "人工测试登录流程" - 需要人在真实环境测试
- "提交PR等待审核" - 需要他人审批
- "手动部署到生产环境" - 需要人工操作
- "联系运维团队开通权限" - 需要协调他人

**判断依据**：描述中暗示 Agent 无法自主完成，而非简单的关键词匹配

## 分析要点

1. **对比历史变化**：
   - 哪些任务的状态发生了变化？
   - 是否有任务反复变化？
   - 整体进度是前进还是原地打转？

2. **识别循环模式**：
   - 测试失败 → 修复 → 测试失败（同样的测试）
   - 实现功能 → 回滚 → 重新实现
   - 文档更新 → 恢复 → 再次更新

3. **评估验收状态**：
   - 如果涉及测试，测试是否在反复失败？
   - 失败原因是否相同？是否在尝试不同的修复方案？

## 输出格式

只输出一个单词和简短原因（不超过50字）：

```
continue
```

或

```
adjust: [原因，如"测试失败循环3轮"]
```

或

```
stop: [原因，如"所有任务已完成"]
```
